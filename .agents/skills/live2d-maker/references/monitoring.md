# 巡检与恢复

本页供启动任务和宿主每两小时唤醒的 agent 使用。启动者将实际 skill 路径、版本、任务路径、运行根目录、任务名和实际定时任务 ID 传入巡检上下文；不要依赖上次对话仍然存在。原绘图任务及各阶段验收要求不变。

## 巡检任务

1. 从 skill 根目录执行 `pnpm start --name <name> --dir <运行根目录> --status --json`。读取任务的 `monitor.md`、总控 `run.json`，结合唯一主日志 `workflow.log` 尾部和当前管线的报告／错误确定实际阶段。旧版本仍在运行的后台任务可能写入 `service.log`；查询返回实际日志路径和更新时间，按该路径检查，恢复后统一写入 `workflow.log`。若原任务使用独立 CLI 且没有总控记录，直接查看该管线的进程、日志和阶段文件，保留原入口及参数，不为巡检改成整条路线。agent 工具和网关活动也在 `workflow.log` 中，不必再寻找独立的可读 agent 日志。总控记录是进度摘要；raster 的 `.running`、`.completed` 和 review/repair 报告、part 的分组树及检查产物仍是恢复依据。
2. 正常推进则简要通报当前阶段和最近实质进展。`.running` 只表示未完成，不能证明进程活着；进程暂时没有输出也不能证明卡死。PID 存活检查不能验证进程身份，必要时核对命令、启动时间、子进程及日志。不要以固定沉默时长中止仍在绘画的任务，也不要重复启动正在自动退避重试的管线。
3. 失败或中断则检查最后模型消息、threadId、当前交付与暂存文件，找到具体原因并执行可恢复操作，再以原入口、原路线和相同 `--name` / `--dir` 续跑；总入口使用 `--background`，独立 CLI 采用宿主可持续执行的方式。当前阶段结束后总调度会自行推进下一条，不必每两小时手动切阶段。
4. 在 `monitor.md` 追加时间、发现的问题、采取的动作和恢复结果，向用户通报。只有修改记录而不恢复可恢复的问题，不算完成巡检。
5. 按[工作台说明](workbench.md)检查页面可达、追踪目录和所选任务一致；连接故障与制作故障分别处理，不能因为网页断开就重置绘图。
6. 完成所选路线后核对 KRA、PNG 和报告，查看结果、给出工作台任务页与实际文件入口并关闭本任务定时检查。用户取消时不再重启任务，核实当前进程身份后停止本任务并关闭定时检查。

总控用心跳锁防止同名任务重复启动。意外退出后锁最多约 30 秒过期；活跃锁冲突先检查实际进程，不直接删除锁。同一任务的独立管线 CLI 不受总控锁保护，不要同时启动独立入口或在其运行中执行恢复操作。

## 恢复原则

- 网络断流、服务过载和临时限流已有自动退避重试，保留原 thread 和文件。若进程已退出，修正原因后续跑；不要重置已完成阶段。
- 模型意外停下或误解正常绘制任务时，整理实际输入、目标和未完成项，给出准确、中性的交接后重试。保留真实任务含义，不规避提供商的内容限制。真实缺少权限或凭证时明确告诉用户缺什么，不能反复空转。
- 工具不可用、Krita 环境或输出路径错误，先核实并修正已获授权范围内的配置，复用 `monitor.md` 中记录的安装方案、路径和显示环境。缺少 Krita 或操作组件时按 [安装与前置](setup.md) 准备方案，先确认再安装；有桌面优先推荐官方原生安装包配合 computer use。已有针对本机和该方案的确认可沿用，不重复询问；等待必要确认期间不能擅自安装或切换方案。脚本仍只检查明确传入的路径。Python 优先复用宿主，缺少时验证 Krita 内置脚本环境；只补实际脚本需要的模块。Nano 透明后处理使用 Node／Sharp 双背景差分；失败时按日志检查两次生图请求、背景和图像尺寸，保留原图后续跑，不安装 Python 抠图包。缺少上游时按报错执行上游或将用户提供的产物放到指定位置；不能伪造产物。
- 上下文／图片上限先按下节核对实际配置和压缩日志；不要把普通重试当作压缩。若绘制 thread 持续拒绝、历史不可恢复或上下文损坏，可按后面的交接步骤换 thread，保留所有工作。相同失败原样重复没有进展时应诊断或交接，不无限启动相同请求。
- 工件缺失或报告无效时，用具体文件和最后消息判断是继续绘制、重新生成报告还是补充上下文。需要重做某个正式 review/repair 报告时，先将原报告和原因归档，再删除该报告让原调度接续；不能改写结论冒充通过、增加第三轮 review 或绕过交付校验。
- 有必要重启卡住的进程时，先核实它确实属于本任务，终止总调度并确认其子进程退出后再恢复。不凭保存的 PID 直接杀进程。网页“停止”只适用于网页 worker 启动的任务；CLI 启动的任务仍需处理原进程。

## 配置与图片超限诊断

先定位实际执行的 skill 和原启动环境，运行 `pnpm env:check`，对照 `monitor.md` 中已确认的配置；参数含义和覆盖顺序见[生效配置核对](workflow-details.md#生效配置核对)。命令只读展示配置，不替代 CLI 登录、补丁能力和实际绘图验证。

| 现象 | 检查与恢复 |
| --- | --- |
| `Exceeded maximum number of images (50)` | 检查图片阈值是否留空、被 shell 覆盖或在另一份 skill 中配置。已确认此上限的环境使用 49，检查子进程生效值和补丁 `image_compaction_version: 2`。修正后先续原 thread，不删产物或阶段目录。 |
| `Response API in-stream error`，没有具体原因 | 先查看 `workflow.log` 的“错误详情”和对应请求的 `result.json`；Codex、Claude Code、AGV 共用错误保留能力，按各 CLI 实际返回保留错误码、类型、参数、状态、原因链和最后模型消息。若仍只有通用断流文案，检查原始 API 与代理事件，不能据此认定网络超时或图片上限。外部 LiteLLM 可使用[错误透传回调](../patches/litellm/README.md)兼容“先空 `response.failed`、后详细 `error`”；按真正的错误恢复，可用保存的事件做本地模拟验证。 |
| 有补丁却没有图片压缩日志 | 区分能力与启用状态。补丁安装不启用阈值；检查 `codex.imageCompaction`。普通请求前达到阈值时应出现 `Layering image guard: N images; compacting with vision...`；此诊断虽通过 CLI error item 传递，不等于整个回合执行失败。 |
| 已进入压缩但回合失败 | 检查随后实际错误及回合结果：鉴权、额度、服务错误或空摘要。保留原 thread、rollout 和图片，修正已获授权的配置后续跑；补丁只在成功得到非空摘要后替换历史。不要把这些错误都解释成 50 张限制。 |
| token 上下文超限 | 与图片张数分开检查，查看实际 Codex provider 的 token 窗口与自动压缩设置。图片保护不解除 token 上限，不凭字符数推断 token 数，也不靠丢弃未总结图片救场。 |
| 没有 `image_generation` 工具，agent 退出且无交付 | 阅读最后模型消息；核对所选 harness、生图模型、API 配置、原生工具能力或补丁版本。修好通道再续跑，不能把退出当完成。 |
| AGV 60 秒响应头超时或 `MINIMAL` 拒绝 | 对照[AGV 补丁说明](../patches/agv/README.md)及[模型与 harness](agent-models.md)，核对实际 CLI 版本、补丁和已配置的兼容项；主请求与 CLI 内部检查分开诊断，不臆造新的工作流超时。 |
| AGV `stream idle timeout` 或旧错误仍留在 `ERROR` 终态 | 未完成的流空闲超时会在原会话自动退避重试。若本轮事件均已结束、最终回复一致，适配器会识别恢复，兼容末尾 `finish` 与多条回复汇总；原始错误仍保留在请求日志中。旧版本已误报停止时，先重放原调用事件并核对交付，再恢复调度；不能仅凭模型说 completed 手工写 `.completed`，绘制后的 review 仍须执行。 |

对于已超出阈值的历史，补丁按容量带图分段：阈值 49、历史 52 张时先压缩 49 张，剩余 3 张保留给下一次普通请求；它们的文字、图序和已完成工具配对一起保留，不重新执行工具。需要验证配置的二进制时，从实际 skill 根目录运行本机模拟：

```bash
python3 patches/codex/image-compaction-smoke.py --codex /绝对路径/补丁版codex --case 52
```

此模拟不访问付费模型、不修改任务。实际恢复后仍核对原 threadId、压缩完成及随后绘图或工具进展；“已启动”或只有 guard 提示不等于压缩已经成功。只有原历史确实无法继续时才用下面的保留产物交接。

## 保留产物地换绘制 thread

只在任务已停止、原 thread 无法有效继续时使用，适用于人物 raster、衣服 raster、穿戴组装和阴影。part 本身根据文件恢复，不需要这个操作。普通中断仍优先续原 thread。

先在任务目录写一份交接 Markdown，说明：原 threadId 与故障证据，当前步骤／正在修复的报告，已完成且应保留的工程，未完成项，必要输入／输出位置，合法拆层及已做调整，需要重看的区域和下一步动作。写具体路径与事实，不只写一句“继续”，不复制大量事件日志或密钥。

```bash
pnpm start --name jianma --dir /绝对路径/运行根目录 \
  --replace-thread clothing-raster-layering \
  --handoff recovery-notes.md --reason "原绘制会话历史无法恢复"
pnpm start --name jianma --dir /绝对路径/运行根目录 --background
```

程序在对应管线 `recovery/<id>/` 保存完整旧配置（含旧 threadId）、交接文档，以及接续时会覆盖的当前提示词、结果、错误和暂存报告，将当前 threadId 清空并登记待交接信息。已有 KRA、图片、日志、`.running`、`.completed` 和 review/repair 进度均保留。新绘制调用接收原阶段任务与交接；若接续修复，同时提供原绘制任务和待修复反馈。新 threadId 随启动事件写回，之后正常续跑继续该 thread。reviewer 仍使用新上下文，不继承绘制交接。

若新 thread 再次失败，可再次交接；每次独立归档，历史链不会丢。命令只准备交接，需另行续跑；全部完成或没有 `.running` 步骤时不能替换。删除 `.completed` 请求从头重画属于另一个操作，会清理该步及后续步骤并取消待交接信息；不要用它处理普通会话中断。

阴影使用 `--replace-thread shadow`，从总控 `run.json` 的 `shadowMode` 定位 `shadow/<模式>/`；必须有明确保存的模式，不猜测分支。只更换当前分支的 thread，保留两张已生成贴图、蒙版分支和各自标记。新会话仍须检查产物和完成报告，再由正常交付检查发布。

## 宿主定时信息

使用宿主实际提供的定时能力创建每 2 小时执行的任务，持续到本次所选路线完成或用户取消。先检查可用工具，不假定某个工具名存在。确认创建成功后，将实际定时任务 ID、间隔、skill 绝对路径、任务绝对路径和恢复命令记在 `monitor.md`，并告知用户。续接任务先核对已有定时任务，避免重复创建。

**宿主没有定时能力时明确告知缺少这项能力，不自行安装 cron 或其他系统定时替代方案，也不声称已经安排检查。** 后台总调度仍可执行；持续巡检不可用需如实说明。

`monitor.md` 另需记录检查指令与启停状态，以及实际 skill 路径／版本、原启动命令与所选范围、Codex 路径／配置目录与启动方式、图片压缩启停状态和阈值、必要 shell 覆盖、Krita 路径及显示环境、工作台 checkout／URL／端口／追踪目录与服务启动方式。只记录配置位置和非敏感启用值，不记录密钥。续跑复用原环境；工作台 checkout 内的另一份 skill 不会自动拥有原 thread 历史。更新 `monitor.md` 不与程序并发改写总控 `run.json`。完成或取消时关闭本任务的定时检查，保留产物和共享工作台服务。
